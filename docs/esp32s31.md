# ESP32-S31 support

LiveKit supports bidirectional Opus audio, room lifecycle, RPC, data packets,
data streams, Wi-Fi, and TLS on ESP32-S31. Two Espressif development boards
have built-in profiles. The Korvo-1 profile also publishes video from its
onboard OV3660 camera.

## Requirements

- ESP-IDF 6.1 with preview targets enabled.
- The ESP-IDF workaround below when using the v6.1 release; do not apply it
  again to a checkout that already contains the branch-predictor fix.
- At least 8 MB of flash and octal PSRAM. The supplied board defaults use
  16 MB flash and 200 MHz octal PSRAM.
- A 2.4 GHz Wi-Fi network.
- LiveKit Cloud or a reachable self-hosted LiveKit server.
- `CONFIG_MBEDTLS_X509_CREATE_C=y`. ESP-IDF 6.1 disables X.509 certificate
  creation by default, but `esp_peer` needs it to generate the self-signed
  DTLS-SRTP certificate.
- `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE=y` and
  `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_CROSS_SIGNED_VERIFY=y` when using the
  Sandbox token server over HTTPS. The supplied S31 defaults set both
  required IDF 6.1 options.

## Supported boards

| Board | Audio | Speaker | RGB LED | Camera |
| --- | --- | --- | --- | --- |
| ESP32-S31-Korvo-1 | ES8389, full duplex | Left/right connectors | One WS2812 on GPIO 37 | Onboard OV3660 |
| ESP32-S31-Function-CoreBoard-1 | ES8311, mono, onboard electret microphone | J9 through NS4150B | One WS2812 on GPIO 60 | External hardware required |

The reusable [`livekit/s31_board`](../components/s31_board/README.md) component
contains these profiles. The
[`custom_hardware_s31`](../components/livekit/examples/custom_hardware_s31/README.md)
example intentionally keeps equivalent audio initialization beside the
application as a template for porting a different S31 design.

## ESP-IDF 6.1 workaround

The selected v6.1 release (`fff9895c82d744c7237be8847347bdd1b07c6643`)
can produce a layout-sensitive `Cache access error`
(`MCAUSE 0x19`) during dual-core flash operations. Apply the repository patch
to the active ESP-IDF checkout before building:

```sh
S31_PATCH="$(pwd)/tools/esp-idf-patches/esp-idf-v6.1-s31-branch-predictor.patch"
git -C "$IDF_PATH" apply --check "$S31_PATCH"
git -C "$IDF_PATH" apply "$S31_PATCH"
```

PowerShell uses `$env:IDF_PATH` instead:

```powershell
$s31Patch = (Resolve-Path tools/esp-idf-patches/esp-idf-v6.1-s31-branch-predictor.patch).Path
git -C $env:IDF_PATH apply --check $s31Patch
git -C $env:IDF_PATH apply $s31Patch
```

The development revision `9bf0c0eb952fe4c075daf20e065ceb27a42ba8bf` already
contains the branch-predictor disable calls; it does not need this patch.
For a different revision, inspect the source and run the patch check before
applying it. See [esp-idf#18948](https://github.com/espressif/esp-idf/issues/18948)
for upstream context. Keep local patches isolated from other IDF projects.

## Configure, build, and flash

Activate an ESP-IDF 6.1 environment and enter an example directory.

On Windows, use a short project path or enable long-path support if the
repository is in a deeply nested directory. Dependency packages include nested
examples that can exceed the
legacy 260-character path limit even when the application's source paths fit.

```sh
idf.py --preview set-target esp32s31
idf.py --preview menuconfig
idf.py --preview build
idf.py --preview -p PORT -b 921600 flash monitor
```

Replace `PORT` with the board's serial port. Lower the baud rate if the USB
connection is unreliable.

In `menuconfig`:

1. Under **LiveKit Example Utilities**, select Wi-Fi and enter the SSID and
   password.
2. Under **LiveKit Example**, choose **Sandbox token** and enter
   its token server ID, or choose a pre-generated server URL and token.
3. Select `ESP32_S31_KORVO_1` or
   `ESP32_S31_FUNCTION_COREBOARD_1` where the example exposes a codec-board
   type.

The generated `sdkconfig` is ignored by Git, but it contains credentials. Do
not commit it or distribute firmware containing personal credentials. A
production device should use provisioning and protected credential storage.

### Function-CoreBoard-1 defaults

For `minimal` and `voice_agent`, add the Function-CoreBoard defaults when
performing a clean command-line build:

```sh
idf.py --preview -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.esp32s31;sdkconfig.defaults.esp32s31.function_core" build
```

The `custom_hardware_s31` example instead uses
`sdkconfig.defaults.function_core`.

Use a separate build directory and generated configuration for each board to
avoid retaining the previous board's settings. For example, from `minimal`:

```sh
idf.py --preview -B build-core -D IDF_TARGET=esp32s31 -D SDKCONFIG=build-core/sdkconfig -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.esp32s31;sdkconfig.defaults.esp32s31.function_core" build
idf.py --preview -B build-core menuconfig
idf.py --preview -B build-core -p PORT -b 921600 flash monitor
```

Named `build-*` directories are ignored. Keep each example's
`managed_components` directory independent; do not share it with other
examples using directory links. Run different configurations of the same
example sequentially because they share its dependency lock and managed files.

## Examples

- `minimal`: bidirectional Opus audio on either supported board.
- `voice_agent`: bidirectional voice-agent interaction, CPU temperature, and
  board-aware RGB LED control on either supported board.
- `custom_hardware_s31`: manual codec/I2S porting template and optional audio
  wiring diagnostics for either supported board.
- `minimal_video`: bidirectional audio plus 240 x 240 H.264 publication from
  the Korvo-1 onboard camera. Function-CoreBoard-1 has no onboard camera and
  requires an external camera and a board-specific adapter.

### Audio wiring diagnostics

The boot-time speaker and microphone diagnostics live in
`custom_hardware_s31`, not in the production-oriented voice-agent example.
They are disabled by default. In that example's `menuconfig`, enable
**speaker channel self-test** to play a 180 Hz channel sweep. On
Function-CoreBoard-1, **microphone level self-test** captures five seconds and
prints peak and RMS levels without storing or transmitting the samples.

## Host interoperability test

### Shared audio path

All four S31 examples keep the hardware sample rate at 48 kHz. Without AEC,
capture and playback use 16-bit stereo. With Korvo AEC, capture uses four
16-bit words in two 32-bit I2S slots to include the codec's appended DAC
references; playback keeps 16-bit stereo PCM in the extended slots.
Function-CoreBoard-1 retains two 16-bit slots and has one microphone and one
speaker. The normal outgoing Opus default remains 16 kHz mono; `esp_capture`
and `av_render` handle format conversion independently of the hardware clock.

Playback uses `livekit_s31_audio_render_alloc()` from `s31_board`, including in
the custom-hardware template, which still initializes its own codec and pins.
This adds a 64 KiB ring, a 4 KiB writer-task stack, and a 200 ms PCM prefill
target. Empty queues re-prime; a 200 ms idle deadline or end-of-stream releases
short tails. It does not implement AEC, mixing, or video display.

Component-based examples configure capture through
`livekit_s31_board_configure_capture()`. Without AEC, Korvo's left microphone
slot is duplicated before mono conversion, preserving frame size and timing.
Korvo and Function-CoreBoard microphone gain settings default to 30 dB;
adjust them for the microphone placement and enclosure.

### Running the host test

Enable **data/RPC interoperability test endpoints** in the `voice_agent`
firmware, use room `esp32-interop` and device identity `esp32-device`, then run:

```sh
cd tools/interop-test
npm install
export LIVEKIT_TOKEN_SERVER_ID='<development-token-server-id>'
node ./interop-test.mjs --audio
```

In PowerShell, set the environment variable with:

```powershell
$env:LIVEKIT_TOKEN_SERVER_ID = '<development-token-server-id>'
```

The harness verifies RPC, reliable and lossy packets, text and byte streams,
and optionally bidirectional audio. See the
[`interop-test` README](../tools/interop-test/README.md) for recovery, LED,
audio-soak, and track-lifecycle options.

## Validation scope

The hardware validation matrix covers the following capabilities. Results
must identify the exact source, firmware, configuration and dependency set;
passing an earlier candidate does not certify a later refactor.

- Korvo-1 and Function-CoreBoard-1 Wi-Fi, HTTPS token acquisition, room join,
  leave/rejoin, RPC, packets, streams, and bidirectional Opus audio.
- Korvo-1 ES8389 output and Function-CoreBoard-1 ES8311 microphone/J9 output.
- RGB control on the supported board profiles.
- Korvo-1 OV3660 detection, 240 x 240 capture, software H.264 publication,
  exposure, orientation, and a three-minute watchdog-free stream.

## Known limitations

- Acoustic echo cancellation is controlled by `CONFIG_LK_EXAMPLE_ENABLE_AEC`.
  It defaults to enabled in the examples that play remote audio while
  capturing, `voice_agent` and `minimal_video`, and to disabled in `minimal`
  and `custom_hardware_s31`, where it can be switched on. The source uses esp-sr
  VOIP_HIGH_PERF with aggressive nonlinear processing and filter length 4.
  The standalone esp-sr source preserves the native 48 kHz sample rate,
  separately filters microphone and DAC-reference capture slots to 16 kHz,
  and publishes mono echo-cancelled audio. Enabling it also enables the
  Function-CoreBoard codec's internal DAC reference. This digital reference
  does not require a second speaker. Korvo selects mic L and DAC L from its
  four-word capture; mono voice must be sent identically to both speaker
  channels. Independent stereo echo cancellation is not implemented.
  AEC-enabled adapters reserve 24 DMA buffers of 240 native frames in each
  direction (120 ms capacity at 48 kHz) to tolerate capture-processing stalls.
  This is 120 ms total capacity per direction, increased from 30 ms (90 ms
  additional capacity), not 120 ms of added latency. The adaptive state uses
  PSRAM; aligned PCM buffers and DMA use internal RAM. There is no capture
  prefill requirement. Both boards' voice-agent firmware passed bounded
  simultaneous playback and near-end speech listening tests with AEC on.
  Both boards also passed conversation sessions exceeding ten minutes with
  no observed unsolicited replies or watchdog failures. Korvo software H.264
  plus AEC passed a continuous 629.788-second audio/video run, with clear
  overlapping-speech microphone returns accepted near the start and end.
- Function-CoreBoard audio is mono. Its microphone gain may need enclosure-
  specific tuning.
- Video subscription and display rendering are outside the initial port.
- Function-CoreBoard video needs an external DVP camera, its signal and power
  wiring, and a matching `esp_video` adapter; no reference pin mapping is
  provided here.
- The Korvo-1 video profile targets software H.264 at 240 x 240 and 10 fps.
  With AEC enabled, an external subscriber measured approximately 6–7 fps
  in two 200-second runs and 6.48 fps over the continuous 629.788-second run.
  Those earlier runs did not achieve the configured 10 fps target. The
  v0.3.11 refresh averaged 10.017 fps over 628.216 seconds with AEC enabled,
  continuous microphone reception and no logged watchdog errors. This was
  not a controlled performance comparison or a repeat of overlap listening.
  See [refresh validation](s31-refresh-validation.md) for its scope.
  Software video encoding shares
  processor resources with audio and network processing; further FPS tuning
  is deferred.
- The SDK subscribes to one remote audio track at a time; simultaneous-track
  selection or mixing is not implemented.
- Occasional playback-onset pops have been reported; pop suppression is not
  implemented. Test normal speech at the intended gain and speaker volume.
- Build and other CPU-intensive host work can disrupt real-time test audio.
  Complete builds before listening tests and measure sender timing before
  attributing a playback problem to the device.
